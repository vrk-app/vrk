# ADR-0002: MVP Scope Guardrails

Статус: accepted  
Дата: 2026-04-11

## Контекст

PRD и roadmap задают строгий MVP, но `README.md` и `BACKEND.md` содержат более широкие идеи для будущего развития. Для автономной разработки без постоянного участия человека нужен жесткий scope fence.

## Решение

Считать для MVP обязательными следующие рамки:

- заявка является центральным объектом системы;
- одна заявка содержит один вид работ;
- одна заявка назначается одному подрядчику;
- к заявке можно привязать несколько единиц оборудования;
- договор определяет допустимого подрядчика и контекст маршрутизации;
- отдельная смета существует только для внеплановых работ;
- приемка результата выполняется внутри системы без юридически значимой ЭП;
- web-контур и field-контур развиваются вместе с backend, но не заменяют его.

Считать вне MVP:

- КЭП/юридически значимую ЭП;
- multi-contractor orchestration внутри одной заявки;
- multi-work-type requests;
- глубокую отдельную метрологическую платформу;
- full ERP/EAM replacement;
- обязательный AI-модуль до доказанного MVP.

## Обоснование

Такие рамки прямо следуют из `docs/PRD-MVP.md` и `docs/roadmap.md` и удерживают объем реализации в пределах достижимого roadmap.

## Последствия

- Любая новая фича, нарушающая эти ограничения, требует отдельного ADR и вероятно уже относится к post-MVP.
- Stage-spec для следующих этапов не должен молча расширять объектную модель за эти границы.
