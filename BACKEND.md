# 1 Общее описание

Бэкенд реализуется в виде монолита с модульной архитектурой, предоставляющего REST API для веб-интерфейса, взаимодействие – через JSON.

# 2 Технологический стек

- **Язык программирования:** Go (Golang)
- **Фреймворк для REST API:** chi
- **База данных:** PostgreSQL (основная), Redis (кеширование)
- **Файловое хранилище:** S3
- **Аутентификация:** JWT
- **Документы:** генерация PDF/Word на основе шаблонов

**Интеграции:**

- 1С (Перенос данных об оборудовании), REST API
- С внешним ИИ-сервисом (для прогнозирования)

# 3 Структура системы

Система должна иметь модульную структуру, включающую следующие модули:

- Модуль авторизации и управления пользователями (Auth)
- Модуль заявок (Applications)
- 3. Модуль чек-листов (Checklists)
- 4. Модуль коммуникаций (Communication)
- 5. Модуль отчётности (Reports)
- 6. Модуль аналитики (Analytics)
- 7. Модуль складского учёта (Warehouse)

# 4 Модули

## 4.1 Модуль авторизации и управления пользователями (Auth)

### Аутентификация

Вход по email и паролю, генерация JWT-токенов. Также должна быть реализована двухфакторная аутентификация (2FA) через email: после успешного ввода пароля на почту высылается одноразовый код, подтверждение которого даёт access токен.

Пароли хранятся в базе данных в захэшированном виде с использованием bcrypt. Access-токен передаётся в заголовке Authorization: Bearer <token>. При выходе из системы или смене пароля все токены пользователя аннулируются.

Блокировка учётной записи после нескольких неудачных попыток входа. Возможность разблокировки администратором.

### Роли пользователей, авторизация

Пользователи делятся на две основные группы: Заказчики и Подрядчики. У каждого пользователя есть одна основная роль, вышестоящие пользователи могут менять роли нижестоящим (в рамках своей иерархии). Доступ к ресурсам (заявкам, оборудованию, чек-листам и т.д.) определяется принадлежностью пользователя к структурной единице и иерархией (вышестоящий видит всё, что ниже). Необходимо реализовать возможность выдать пользователю доступ только для чтения или полный доступ отдельно для оборудования (складской учет), заявок (сюда же чеклисты и комментарии к заявкам), управления другими пользователями ниже по иерархии. Каждому пользователю предоставляется минимум прав, необходимых для выполнения его обязанностей.

### Регистрация

Должна быть возможность регистрации для организаций заказчика и подрядчика (самые верхние по иерархии у заказчика и подрядчика).

Регистрация остальных пользователей производится вышестоящими ролями. Самостоятельная регистрация не предусмотрена. При создании пользователя указываются: ФИО, email, пароль (изначально генерируется автоматически, должна быть возможность смены пароля через email), роль, привязка к структурной единице. Владелец организации может дать права руководителю, который дальше сам зарегистрирует своих сотрудников. Для заказчика – ответственное лицо выдает регистрацию/смену пароля, у подрядчиков сотрудники сами меняют пароль).

### Управление структурными подразделениями

- У заказчиков: организация создаётся при регистрации. Глава организации может создавать/редактировать/удалять ведомства ниже по иерархии (главы ведомств ниже по иерархии также могут создавать ведомства ещё ниже по иерархии).
- У подрядчиков аналогично: главная организация создаётся при регистрации, остальные подразделения создаются главой организации и другими сотрудниками вниз по иерархии.

## 4.2 Модуль заявок

### Договоры

Договоры между заказчиками и подрядчиками должны быть загружены в систему заказчиками.

Глава организации (или кто-то кому он дал доступ) загружает договор в форму. Скан/фото/docx/pdf договора хранится в S3, в таблице основой бд хранятся:

- `fileURL` - ссылка на договор в S3,
- `number` - номер договора (указывается в форме главой организации),
- `agreement_start_date` – начало действия договора (договор может быть добавлен заранее, до начала действия),
- `agreement_end_date` - дата окончания договора (указывается в форме главой организации)
- `organization_customer_id` - организация заказчик,
- `organization_contractor_id` - организация подрядчик.
- `planned_completion_date` - планируемая дата заверешния
- `completion_date` - дата завершения

### Заявки

Заявка создаётся мастером депо для выполнения работ подрядчиком. Заявка создается на основе договора, можно выбрать только подрядную организацию у которой есть договор с заказчиком. Ответственный в подрядной организации должен принять заявку, затем он выбирает бригаду, ответственный бригады ставится в заявку.

**Поля заявки:**

- `id` (заполняется автоматически)
- `agreement_id` - id договора (при создании заявки человек создающий заявку указывает номер договора)
- `number` - нужно генерировать удобный уникальный номер для заявки, чтобы заказчик и подрядчик могли использовать его при общении и в документах
- `status_id` - статус заявки (создана, принята подрядчиком, назначена бригада, отклонена, в работе, что-то с документами, завершена, (список заявок будет)) (очень подробные статусы не нужны так как можно отслеживать процесс выполнения по заполнению чеклистов)
- `application_type_id` - тип заявки (ремонт/обслуживание/поверка)
- `responsible_brigade_id` - ответственная бригада, назначается подрядчиком после принятия им заявки
- `responsible_user_contractor_id` - ответственный за заявку пользователь у подрядчика, назначается автоматически (мастер депо при создании заявки указывает организацию подрядчика)
- `user_client_id` - мастер депо (тот кто создает заявку), назначается автоматически

Имеется связь многие-ко-многим с таблицей оборудования (у одной заявки может быть несколько оборудований).

### Ограничения и проверки

**При создании заявки:**

- Обязательные поля должны быть заполнены.
- Проверка договора:
  - договор с указанным номером должен существовать.
  - `end_date`, если указана, больше или равна текущей.
  - организация-заказчик из договора должна совпадать с организацией, к которой относится депо мастера, создающего заявку.
  - оборудование с указанным `equipment_id` должно существовать и принадлежать депо, от которого создаётся заявка.

**При назначении бригады:**

- Бригада (`responsible_brigade_id`) должна принадлежать организации-подрядчику, указанной в заявке.

### Статусы заявки

- Не должно быть непредусмотренных переходов с пропуском статусов и назад по статусам.
- В `in_progress` заявка должна перейти автоматически, когда первый пункт любого связанного чек-листа отмечен как выполненный.
- В `completed` – когда все связанные чек-листы имеют статус `completed`. Либо по ручному действию заказчика (с предупреждением что не все чеклисты заполнены).

### Связь с другими модулями

Заявка привязана к конкретному оборудованию (`equipment_id`), что позволяет вести историю обслуживания/ремонта/поверки по каждому объекту. В процессе жизненного цикла заявки должны изменяться статус оборудования и информация о нем (даты последних работ и т.д.)

Заявки служат основным источником для расчёта KPI бригад и подрядчиков: количество выполненных заявок, средняя длительность, соблюдение сроков, доля заявок с доработками и т.д.

## 4.3 Модуль чеклистов

Модуль чек-листов предназначен для формализации процесса выполнения работ по заявкам. Он обеспечивает создание шаблонов чек-листов, генерацию экземпляров под конкретную заявку, сбор данных от исполнителей и передачу собранной информации в смежные модули (заявки, складской учёт, отчётность, аналитика).

### Шаблоны чек-листов

Шаблоны чек-листов создаются администраторами системы (шаблон обозначает какие пункты есть в чек-листе) для стандартизации процессов обслуживания, ремонта и поверки. Каждый шаблон соответствует определённому типу работ (ремонт/поверка/обслуживание/приёмка), также могут появится разные шаблоны для разных организаций. Шаблоны могут создаваться как для подрядчика, так и для заказчика (например, чек-лист приёмки).

Имеется поле привязки к организации, если организации потребуется свой шаблон. При создании заявки он должен выбираться только для этой организации (есть основные шаблоны для всех и кастомные для определенных организаций, которым необходим другой шаблон для чего-либо).

**Поля:**

- `id` - уникальный идентификатор шаблона
- `name` - название шаблона
- `type` - тип работ, для которых предназначен шаблон (ремонт, ТО, поверка, приёмка).
- `organization_id` - если шаблон для организации

### Пункты шаблона

Каждый пункт определяет, что именно нужно сделать, какой тип данных ожидается, и является ли он обязательным.

**Поля:**

- `id` - Уникальный идентификатор пункта
- `template_id` - ссылка на `checklist_templates`
- `order` - порядковый номер пункта в чек-листе
- `item_type` - тип пункта: `checkbox` (отметка о выполнении), `text` (текстовый комментарий), `photo` (фото).
- `required` - обязательность заполнения
- `title` - краткое описание действия (например, «Проверить крепления», «Сделать фото до ремонта»)
- `description` - подробная инструкция (опционально)

### Экземпляры чек-листов

При создании новой заявки система автоматически создает экземпляры чек-листов на основе нужных шаблонов (если для организации заданы кастомные то берутся они, если нет то общие). Выбор шаблонов определяется типом заявки.

**Поля:**

- `id` - уникальный идентификатор экземпляра (заполняется автоматически)
- `request_id` - id заявки (заполняется автоматически)
- `template_id` - id шаблона (заполняется автоматически)
- `completed` - завершён или нет
- `started_at` - время начала заполнения (первый сохранённый пункт)
- `completed_at` - время окончания заполнения

### Пункты экземпляров чек-листов

Хранит фактические данные, введённые исполнителем по каждому пункту чек-листа. Запись создаётся для каждого пункта шаблона при создании экземпляра.

**Поля:**

- `id` - уникальный идентификатор
- `checklist_instance_id` - ссылка на `checklist_instances`
- `is_checked` - для типа `checkbox` — отметка о выполнении (`true/false`)
- `text_value` - для типа `text` — введённый текст
- `completed_at` - время заполнения пункта

Фотографии одного пункта хранятся в отдельной таблице `Checklist_Instance_Item_Photos` (так как может быть несколько фотографий у одного пункта)

### Ограничения и проверки

- При создании экземпляра чек-листа копируются все пункты шаблона с их параметрами. Изменение шаблона после создания не влияет на уже существующие экземпляры.
- Обязательные пункты (`required = true`) должны быть заполнены для перевода статуса экземпляра в `completed`. Система не позволяет завершить чек-лист, пока все обязательные пункты не будут отмечены.
- Права доступа: заполнять чек-листы может только ответственный член бригады, назначенный на заявку. Просматривать – все участники заявки согласно их ролям (и те, кто выше по иерархии).

### Связь с другими модулями

- Отчётность: данные из заполненных чек-листов используются для автоматического формирования актов выполненных работ, авансовых отчётов и других документов. В частности, перечень использованных материалов, трудозатраты подставляются в шаблоны документов.
- Аналитика: на основе данных чек-листов рассчитываются KPI бригад и формируются отчёты для руководителей.

## 4.4 Модуль коммуникации

Модуль обеспечивает взаимодействие между участниками заявки (заказчиками и подрядчиками) путём создания тематических обсуждений (тредов) и обмена сообщениями с возможностью прикрепления файлов. Он служит для оперативного уточнения деталей, согласования изменений, обмена документами и фиксации переписки в контексте конкретной заявки.

### Треды обсуждений

Треды может создавать любой пользователь, имеющий доступ к заявке.

- `id` - уникальный идентификатор треда
- `request_id` - ссылка на заявку, в рамках которой создан тред
- `title` - краткое название/тема обсуждения
- `is_closed` - флаг, закрыт ли тред (если закрыт, добавление новых комментариев запрещено)
- `created_by` - пользователь, создавший тред

### Сообщения

- `id` - уникальный идентификатор комментария
- `thread_id` - ссылка на тред
- `user_id` - пользователь
- `text` - текст сообщения
- `answered_to` - ссылка на другой комментарий, если это ответ на конкретное сообщение

Ссылки на прикрепляемые файлы будут храниться в отдельной таблице `Comment_File_URLs`.

## 4.5 Модуль отчетности

Модуль отчетности предназначен для автоматического формирования документов на основе шаблонов и данных, собранных в процессе выполнения заявок (заполненные чек-листы, информация о заявке, оборудовании, организациях). Он позволяет пользователям (как заказчикам, так и подрядчикам) получать готовые акты, счета, отчеты и другие документы без ручного заполнения.

### 4.5.1 Сущности и структура БД

#### 4.5.1.1 Шаблоны документов (document_templates)

Шаблоны создаются администраторами системы или уполномоченными пользователями для стандартизации выходных документов. Шаблон представляет собой файл в формате DOCX, содержащий специальные метки-плейсхолдеры, которые при генерации заменяются на фактические данные. Хранение осуществляется в объектном хранилище (S3), в базе данных сохраняется только ссылка.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `UUID (PK)` | Уникальный идентификатор шаблона |
| `name` | `VARCHAR(255)` | Название шаблона (например, «Акт выполненных работ», «Счет на оплату») |
| `description` | `TEXT` | Описание, для каких целей предназначен шаблон |
| `file_url` | `TEXT` | Ссылка на файл шаблона в S3 |
| `template_type` | `ENUM` | Тип документа |
| `created_by` | `UUID (FK)` | Пользователь, создавший шаблон |

#### 4.5.1.2 Сгенерированные документы

При генерации документа создаётся запись, фиксирующая факт формирования, и сохраняется итоговый файл (в формате PDF, DOCX, PNG) в S3.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `UUID (PK)` | Уникальный идентификатор сгенерированного документа |
| `application_id` | `UUID (FK)` | Ссылка на заявку |
| `template_id` | `UUID (FK)` | Ссылка на шаблон, использованный при генерации |
| `file_url` | `TEXT` | Ссылка на итоговый файл в S3 |
| `file_format` | `VARCHAR(10)` | Формат файла (`pdf`, `docx`, `png`, `jpg`) |
| `generated_at` | `TIMESTAMP` | Дата и время генерации |
| `generated_by` | `UUID (FK)` | Пользователь, инициировавший генерацию |

### 4.5.2 Функциональность

#### 4.5.2.1 Управление шаблонами

Создание шаблона: Администратор загружает файл шаблона (DOCX), заполняет название, описание, выбирает тип и связанную сущность. Система сохраняет файл в S3 и создаёт запись в `document_templates`.

#### 4.5.2.2 Генерация документа

Пользователь (например, мастер депо или руководитель подрядчика) в интерфейсе заявки или чек-листа нажимает кнопку «Сформировать документ» и выбирает подходящий шаблон из списка доступных (фильтрованных по типу и связанной сущности).

**Система:**

- Проверяет права доступа (пользователь должен иметь доступ к заявке/чек-листу).
- Собирает все необходимые данные:
  - из заявки: номер, дата создания, описание, оборудование, заказчик, подрядчик, ответственные лица и т.д.;
  - из чек-листов: перечень выполненных работ, использованные материалы (с количеством), фото, комментарии;
  - из организационной структуры: наименования организаций, адреса, контактные данные;
- Подставляет данные в шаблон. Для этого используется библиотека, работающая с DOCX-файлами. Плейсхолдеры в шаблоне имеют вид `{{field_name}}` и заменяются на соответствующие значения.
- Генерирует итоговый документ. По умолчанию можно сохранять в формате DOCX, но также может быть конвертация в PDF (если требуется).
- Загружает готовый файл в S3, создаёт запись в `generated_documents`.
- Возвращает пользователю ссылку на скачивание.

#### 4.5.2.3 Просмотр и скачивание сгенерированных документов

Пользователь может просмотреть список всех сгенерированных документов по заявке (или в общем списке) и скачать их. Документы не редактируются, доступны только для чтения.

## 4.6 Модуль аналитики

Модуль аналитики предназначен для сбора, агрегации и визуализации данных о работе системы. Он предоставляет пользователям (как заказчикам, так и подрядчикам) статистическую информацию и ключевые показатели эффективности (KPI), необходимые для контроля качества обслуживания, оптимизации процессов и принятия управленческих решений. На основе данных из других модулей (заявки, чек-листы, оборудование, складской учёт) формируются отчёты, графики и прогнозы, включая интеграцию с внешним ИИ-сервисом для предсказания отказов оборудования. Действия подрядчика должны отражаться в истории обслуживания заказчика.

### 4.6.1 Принцип работы

Модуль аналитики не хранит первичные данные, а получает их из других модулей системы по запросу или с определённой периодичностью. Основные операции:

- Сбор данных – извлечение информации из БД (таблицы заявок, чек-листов, оборудования) с возможностью фильтрации по датам, организационным единицам, оборудованию и другим параметрам.
- Агрегация и вычисление – расчёт метрик (количество, средние значения, проценты, динамика) с использованием SQL-запросов.
- Кэширование – для часто запрашиваемых отчётов и больших объёмов данных предусмотрено кэширование результатов в Redis или предварительный расчёт агрегатов в отдельных таблицах.
- Предоставление данных API – REST-эндпоинты возвращают структурированные данные (JSON) для отображения на фронтенде (графики, таблицы) или для экспорта (PDF, Excel).
- Интеграция с ИИ – подготовка и отправка исторических данных в ИИ-сервис, получение прогнозов и их сохранение/отображение.

### 4.6.2 Примеры метрик и отчётов по ролям

Окончательный список метрик будет уточняться в процессе разработки, примерно:

**Для заказчика**

- **Общие показатели:**
  - Количество заявок за период (всего, по типам, по статусам).
  - Среднее время выполнения заявки (от создания до завершения).
  - Доля заявок, выполненных в срок (согласно желаемой дате).
  - Простои оборудования (суммарное время, когда оборудование находилось в статусе «в ремонте»).
- **По оборудованию:**
  - История ремонтов и обслуживания по каждому объекту.
  - Наработка на отказ – среднее время между отказами.
  - Прогноз следующего отказа или ТО (из ИИ).
- **По подрядчикам:**
  - Статистика подрядчиков по скорости и качеству (количество доработок, отзывы).
  - Затраты по договорам (сумма материалов и работ).

**Для подрядчика**

- **По бригадам:**
  - Количество выполненных заявок за период.
  - Средняя продолжительность выполнения .
  - Загрузка бригад (количество одновременно активных заявок).
  - Эффективность (процент заявок, сданных с первого раза, без доработок).
- **По материалам:**
  - Расход материалов по заявкам (суммарно и по видам).
  - Остатки на складах, прогноз дефицита.
- **Финансовые показатели:**
  - Стоимость выполненных работ (на основе нормативов и фактических затрат).
  - Анализ прибыльности (если есть данные о стоимости материалов и трудозатратах).
- **Графики:**
  - Сравнение бригад по скорости.
  - Динамика выполнения заявок.

**Для руководителей**

- Сводные отчёты по всем подразделениям с детализацией до конкретного подразделения.
- Сравнительный анализ эффективности разных регионов.
- Тренды и прогнозы загрузки.

### 4.6.4 Реализация и хранение агрегатов

На начальном этапе допустимо вычислять большинство метрик в реальном времени при запросе отчёта. Однако для больших объёмов данных и часто запрашиваемых отчётов необходимо использовать кэширование.

**Подходы:**

- Динамический расчёт – каждый запрос к API выполняет SQL-запросы с агрегацией. Просто реализовать, но может быть медленным при большом количестве данных.
- Кэширование результатов – результаты сложных запросов сохраняются в Redis на определённое время. При повторном запросе возвращается кэш.
- Отдельные таблицы, которые обновляются по расписанию (например, каждую ночь) или триггерами при изменениях. Содержат предрасчитанные агрегаты по периодам (день, неделя, месяц) и измерениям. Это наиболее производительный и масштабируемый вариант.

### 4.6.5 Интеграция с ИИ-модулем

Данные отправляются в ИИ-сервис. ИИ-сервис возвращает прогнозную информацию, на дашборде заказчика выводится информация о прогнозируемых отказах.

## 4.7 Модуль складского учета

Модуль складского учета предназначен для ведения количественного учета материалов и запчастей, используемых подрядчиками при выполнении работ, а также для учета оборудования заказчиков. В основе модуля лежат пять таблиц. Все изменения количественных остатков фиксируются в аудите (audit log), что обеспечивает прослеживаемость операций.

### 4.7.1 Описание сущностей

#### 4.7.1.1 Оборудование (Equipment)

Справочник оборудования, принадлежащего заказчикам. Каждая единица оборудования привязана к организации (заказчику) и имеет текущий статус.

- `id` - уникальный идентификатор оборудования
- `name` - наименование оборудования
- `number` - Инвентарный или заводской номер
- `manufacturer` - производитель
- `manufacture_year` - год выпуска
- `organization_id` - организация
- `status_id` - статус оборудования (ссылка на `Equipment_Status`)

#### 4.8.1.2 Статусы оборудования (Equipment_Status)

Возможные состояния оборудования

- `id` - код статуса
- `status` - наименование статуса

#### 4.8.1.3 Склады (Warehouses)

Склады, на которых хранятся материалы. Склады привязаны к организации и могут иметь физическое местоположение. Любой материал должен быть привязан к складу, даже если у них он хранится где-то в мастерской.

- `id` - уникальный идентификатор склада
- `name` - название склада
- `organization_id` - организация
- `location` - адрес или описание местоположения (опционально)

#### 4.8.1.4 Материалы (Materials)

Учетные записи материалов и запасных частей. Каждая запись соответствует конкретному материалу на конкретном складе и содержит текущее количество.

- `id` - Уникальный идентификатор записи материала
- `name` - наименование материала
- `amount` - текущее количество на складе
- `unit` - единица измерения (шт, кг, м, л и т.п.)
- `warehouse_id` - склад, на котором находится материал

#### 4.8.1.5 Связь заявок и оборудования

Cвязь «многие ко многим» между заявками и оборудованием. Одна заявка может относиться к нескольким единицам оборудования, и одно оборудование может фигурировать в нескольких заявках.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `UUID (PK)` | Уникальный идентификатор связи |
| `application_id` | `UUID (FK)` | Ссылка на заявку |
| `equipment_id` | `UUID (FK)` | Ссылка на оборудование |

### 4.8.2 Функциональность модуля

#### 4.8.2.1 Управление справочниками

- Оборудование: создание, редактирование, изменение статуса, просмотр. При изменении статуса оборудования запись фиксируется в аудит-логе.
- Статусы оборудования: предопределенный набор, может дополняться администратором.
- Склады: создание, редактирование, удаление (только если на складе нет остатков).
- Материалы: добавление новой позиции на склад (поступление), редактирование наименования и единицы измерения (если остаток нулевой), удаление (только при нулевом остатке).

#### 4.8.2.2 Поступление материалов

При поступлении новой партии материала на склад пользователь (кладовщик) создает запись в `Materials` или увеличивает количество в существующей. Небходимо проверить, существует ли на данном складе материал с таким же `name` и `unit`. Если существует – увеличить `amount` на величину поступления. Если не существует – создать новую запись с `amount = количество поступления`.

Операция фиксируется в аудит-логе.

#### 4.8.2.3 Списание материалов

Списание материалов происходит в рамках выполнения отчета об использованных материалах. При сохранении такого отчета система, уменьшает `amount` соответствующей записи в `materials`, после списания количество не должно стать отрицательным.

В аудит-лог записывается действие с указанием заявки и количества.

#### 4.8.2.4 Перемещение материалов между складами

Перемещение реализуется как списание со склада-источника и поступление на склад-назначение. Важно обеспечить атомарность операции (транзакция БД).

#### 4.8.2.5 Инвентаризация и корректировка остатков

При обнаружении расхождений фактических остатков с учетными, уполномоченный пользователь может провести корректировку, изменив `amount` напрямую. Такие изменения должны обязательно логироваться с комментарием причины.

#### 4.8.2.6 Отчеты и аналитика

Модуль предоставляет простые отчеты:

- Остатки на складах: список всех материалов с количеством по каждому складу, с возможностью фильтрации.
- Движение материалов: история поступлений, списаний, перемещений за период (выгружается из `audit_log`).
- Расход материалов по заявкам: сколько и каких материалов израсходовано на конкретную заявку или по всем заявкам за период.
- Оборудование по статусам: количество единиц оборудования в каждом статусе.

## 4.9. Модуль уведомлений

Модуль уведомлений отвечает за информирование пользователей о важных событиях, происходящих в системе. На текущем этапе уведомления отправляются на электронную почту (email) всем заинтересованным лицам.

### 4.9.1 Общие принципы

Уведомления отправляются асинхронно, чтобы не замедлять обработку запросов. Для отправки используется внешний SMTP-сервер или API почтового сервиса.

## 4.10 Аудит-лог

Аудит предназначен для регистрации всех значимых действий пользователей в системе. Логи аудита обеспечивают прозрачность, возможность расследования инцидентов, контроль доступа и соответствие требованиям. Записи аудита хранятся в отдельной таблице.

Также у всех таблиц в системе должны быть поля `created_at` и `updated_at`.

### 4.7.1 Сущность и структура БД

Таблица `audit_log`

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `UUID (PK)` | Уникальный идентификатор записи |
| `user_id` | `UUID (FK)` | Пользователь, совершивший действие |
| `action` | `VARCHAR(100)` | Тип действия (например, `'CREATE'`, `'UPDATE'`, `'DELETE'`, `'LOGIN'`, `'LOGOUT'`, `'GENERATE_DOCUMENT'`, `'UPLOAD_FILE'`) |
| `entity_type` | `VARCHAR(50)` | Тип сущности, над которой совершено действие (например, `'request'`, `'checklist'`, `'equipment'`, `'user'`, `'contract'`) |
| `entity_id` | `UUID` | Идентификатор сущности (опционально) |
| `old_values` | `JSONB` | Предыдущие значения полей |
| `new_values` | `JSONB` | Новые значения полей |
| `changes` |  | Краткое описание изменений (опционально) |
| `timestamp` | `TIMESTAMP` | Время совершения действия (по умолчанию `NOW()`) |

# 5. Безопасность системы

Все соединения с сервером осуществляются по протоколу HTTPS .

**Защита от инъекций:**

- Все запросы к БД выполняются через параметризованные запросы (использование подготовленных выражений).
- Входные данные проходят валидацию.
- Следует установить правильные CORS-политики.

**Ограничение частоты запросов (rate limiting):**

- Настроено для всех API-эндпоинтов, особенно для аутентификации (чтобы предотвратить подбор паролей) и для массовых операций.

**Резервное копирование:**

- Регулярное автоматическое резервное копирование базы данных и файлового хранилища (S3).
- Хранение резервных копий в защищённом удалённом хранилище.

**Мониторинг и обнаружение атак:**

- Внедрение системы мониторинга (Prometheus + Grafana).
- Оповещение администратора о нештатных ситуациях (множественные ошибки аутентификации, аномальный трафик).
