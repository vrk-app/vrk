# 1. Назначение документа

`BACKEND.md` фиксирует backend-рамку `MVP` для `VRK Platform` и должен оставаться согласованным с [README.md](/Users/yura-posledov/cursor/vrk/README.md) и [docs/PRD-MVP.md](/Users/yura-posledov/cursor/vrk/docs/PRD-MVP.md).

Документ описывает:

- целевую backend-архитектуру первой версии;
- обязательные доменные модули MVP;
- ключевые сущности и бизнес-правила;
- нефункциональные требования и границы MVP.

`VRK Platform` в `MVP` строится вокруг `заявки` как центрального объекта системы и обслуживает три контура:

- веб-кабинет заказчика;
- веб-кабинет подрядчика;
- мобильный клиент инженера с офлайн-синхронизацией.

# 2. Архитектурная рамка и стек

## 2.1. Архитектурный подход

Backend реализуется как модульный монолит на `Go`, предоставляющий:

- `REST API` для веб-контуров;
- отдельные sync/upload endpoints для мобильного клиента;
- асинхронные фоновые задачи для уведомлений, генерации документов и тяжелых операций.

На старте это предпочтительнее, чем микросервисная схема, потому что:

- домены сильно связаны вокруг одной заявки;
- критично быстро выйти в пилот с минимальной операционной сложностью;
- аудиторский след, права и транзакционные операции проще держать в одном контуре.

## 2.2. Технологический стек

- Язык: `Go`
- HTTP/router: `chi`
- База данных: `PostgreSQL`
- Кэш и технические очереди: `Redis`
- Файловое хранилище: `S3`-совместимое хранилище
- Аутентификация: `JWT access token + refresh token`
- Формирование документов: `DOCX/PDF` на основе шаблонов

## 2.3. Что не считается обязательным для MVP

Следующие вещи архитектурно допускаются, но не должны блокировать запуск первой версии:

- обязательная интеграция с `1С` или другой ERP;
- `AI`-прогнозирование отказов;
- юридически значимая ЭП/КЭП;
- отдельный аналитический сервис;
- сложный ресурсный планировщик смен, географии и компетенций.

# 3. Ключевые ограничения MVP

Backend обязан поддерживать следующие правила из `README` и `PRD`:

- одна заявка относится к одному виду работ: `repair`, `maintenance`, `verification`;
- одна заявка назначается одному подрядчику;
- заявка обязательно содержит хотя бы одну единицу оборудования;
- подрядчик определяется по действующему договору и правилам маршрутизации;
- для внеплановых работ обязателен объект `смета / согласование стоимости`;
- приемка результата выполняется внутри системы без юридически значимой ЭП;
- мобильный контур должен поддерживать офлайн-работу и последующую синхронизацию;
- материалы должны быть видны в контексте заявки с указанием источника.

Дополнительно для backend-проектирования принимаются следующие технические принципы:

- все основные сущности используют `UUID`;
- все таблицы имеют как минимум поля `created_at` и `updated_at`;
- критичные изменения бизнес-сущностей фиксируются в `audit_log`;
- файловые объекты хранятся в `S3`, в БД хранятся метаданные и ссылки;
- tenant-изоляция строится на уровне организации и ее структурных единиц.

# 4. Доменные модули

## 4.1. Авторизация, пользователи и оргструктура

### 4.1.1. Сущности

Минимальный набор сущностей:

- `organizations` - юридические лица и верхнеуровневые организации;
- `organization_business_roles` - бизнес-роли организации: `customer`, `contractor`;
- `organization_units` - структурные узлы дерева организации с типом `region`, `depot`, `service_center`;
- `brigades` - бригады подрядчика;
- `brigade_members` - состав бригады;
- `users` - учетные записи пользователей;
- `user_roles` - системные роли (`system_admin`, `org_admin`, `dispatcher`, `manager`, `engineer`, `acceptor` и т.д.);
- `user_permissions` - доменные права (`applications`, `materials`, `documents`, `users`) с уровнями `read` / `write` / `manage`;
- `refresh_tokens`, `password_reset_tokens`, `invitations`.

### 4.1.2. Правила оргструктуры

Backend должен поддерживать две базовые логики дерева:

- заказчик: `Организация -> Регион -> Депо`;
- подрядчик: `Организация -> Регион -> Сервисный центр -> Бригада`.

При этом модель должна быть расширяемой на будущее, когда одна и та же организация сможет выступать и заказчиком, и подрядчиком. Поэтому роль организации не должна быть зашита одним полем `type`.

### 4.1.3. Аутентификация и авторизация

Для `MVP` достаточно:

- входа по `email/password`;
- выдачи `access token` и `refresh token`;
- сброса пароля по email;
- инвалидации refresh-токенов при смене пароля или ручном завершении сессии;
- rate limiting и временной блокировки после серии неудачных попыток входа.

`2FA` через email может быть добавлена позже, но не должна считаться обязательным требованием `MVP`.

Авторизация должна учитывать одновременно:

- организацию пользователя;
- структурную единицу;
- роль;
- доменные права;
- иерархию просмотра данных сверху вниз.

### 4.1.4. Онбординг пользователей

Для `MVP` предпочтителен контролируемый `B2B`-онбординг:

- верхнеуровневые организации создаются администратором платформы или через ручной онбординг;
- остальные пользователи создаются по инвайту вышестоящими ролями;
- публичная self-service регистрация не является обязательной частью первой версии.

## 4.2. Договоры и маршрутизация заявок

### 4.2.1. Сущности

- `agreements`
- `agreement_scopes`
- `agreement_files`

`agreements` должны хранить минимум:

- `id`
- `number`
- `customer_organization_id`
- `contractor_organization_id`
- `status` (`draft`, `active`, `expired`, `archived`)
- `starts_at`
- `ends_at`
- `default_price_mode` (`planned`, `unplanned`, `mixed`)
- `priority`
- `created_by`

`agreement_scopes` описывает правила применимости договора:

- `agreement_id`
- `region_unit_id` - опционально
- `depot_unit_id` - опционально
- `equipment_type_id` - опционально
- `work_type` - опционально

`agreement_files` хранит загруженные версии договора и приложений.

### 4.2.2. Бизнес-правила

Договор в `MVP` используется не только как вложение, но и как правило маршрутизации. Backend при создании заявки должен уметь:

- найти активные договоры по заказчику;
- отфильтровать их по дате действия;
- проверить совпадение региона, депо, типа оборудования и вида работ;
- определить доступного подрядчика.

Если найден ровно один подходящий договор, подрядчик назначается автоматически.

Если найдено несколько договоров, UI может показать пользователю список допустимых вариантов, но backend должен вернуть только валидные с точки зрения правил маршрутизации договоры.

Если договор не найден, заявка не может быть отправлена подрядчику.

## 4.3. Реестр оборудования

### 4.3.1. Сущности

- `equipment_types`
- `equipment`
- `equipment_statuses`
- `equipment_status_history`

`equipment` должно хранить минимум:

- `id`
- `customer_organization_id`
- `region_unit_id`
- `depot_unit_id`
- `equipment_type_id`
- `name`
- `inventory_number`
- `serial_number`
- `manufacturer`
- `manufacture_year`
- `status_id`
- `commissioned_at`
- `last_service_at`

### 4.3.2. Бизнес-правила

- заявка может быть создана только по оборудованию, существующему в реестре;
- каждая единица оборудования должна принадлежать заказчику и быть привязана к депо;
- история обслуживания оборудования строится через связку `equipment -> applications -> checklists -> documents`;
- для корректной трассировки изменения статуса оборудования должны фиксироваться в `equipment_status_history`.

Оборудование не должно описываться как часть складского модуля: это отдельный продуктовый реестр.

## 4.4. Заявки и приемка результата

### 4.4.1. Сущности

- `applications`
- `application_equipments`
- `application_status_history`
- `application_acceptances`

`applications` должно хранить минимум:

- `id`
- `number` - человекочитаемый уникальный номер
- `agreement_id`
- `customer_organization_id`
- `customer_depot_unit_id`
- `contractor_organization_id`
- `work_type` (`repair`, `maintenance`, `verification`)
- `price_mode` (`planned`, `unplanned`)
- `status`
- `title`
- `description`
- `priority` - опционально для MVP, но желательно заложить сразу
- `created_by`
- `responsible_customer_user_id`
- `responsible_contractor_user_id`
- `responsible_brigade_id`
- `assigned_engineer_user_id` - опционально
- `due_at`
- `completed_by_contractor_at`
- `accepted_by_customer_at`
- `cancelled_at`

`application_equipments` реализует связь `многие-ко-многим` между заявками и оборудованием.

`application_acceptances` хранит факт приемки результата:

- `application_id`
- `accepted_by`
- `accepted_at`
- `comment`

### 4.4.2. Обязательные бизнес-правила

Backend должен валидировать, что:

- у заявки есть хотя бы одна единица оборудования;
- у заявки ровно один `work_type`;
- у заявки ровно один подрядчик;
- подрядчик выводится из выбранного договора, а не задается произвольно;
- оборудование принадлежит заказчику и находится в допустимом контуре договора;
- ответственный и бригада относятся к организации-подрядчику заявки.

### 4.4.3. Статусы заявки MVP

Стартовый набор статусов должен быть согласован с `PRD`:

- `draft`
- `created`
- `assigned_to_contractor`
- `in_progress`
- `estimate_approval`
- `completed_by_contractor`
- `accepted_by_customer`
- `cancelled`

`status_history` обязателен.

Рекомендуемые переходы:

- `draft -> created`
- `created -> assigned_to_contractor`
- `assigned_to_contractor -> in_progress`
- `assigned_to_contractor -> estimate_approval` для внеплановых работ
- `estimate_approval -> in_progress` после согласования сметы
- `in_progress -> completed_by_contractor`
- `completed_by_contractor -> accepted_by_customer`
- любой незавершенный статус -> `cancelled` по правам

Автоматически закрывать заявку только по факту заполнения чек-листов нельзя: в `MVP` требуется явная приемка заказчиком.

### 4.4.4. Приемка результата

Модель приемки в `MVP` должна быть простой:

- подрядчик завершает заявку;
- заказчик просматривает результат, документы, материалы и чек-листы;
- заказчик выполняет явное действие `accept`.

Это означает, что backend обязан различать как минимум два финальных состояния:

- `completed_by_contractor`
- `accepted_by_customer`

## 4.5. Процессные шаблоны, чек-листы и мобильная синхронизация

### 4.5.1. Сущности

- `process_templates`
- `checklist_templates`
- `checklist_template_items`
- `checklist_instances`
- `checklist_answers`
- `checklist_answer_attachments`

`process_templates` нужны потому, что в `README` и `PRD` зафиксированы отдельные процессные шаблоны для ремонта, ТО и поверки. Минимальные поля:

- `id`
- `name`
- `work_type`
- `organization_id` - опционально для кастомизации
- `required_fields_schema` (`JSONB`)
- `checklist_template_ids`
- `required_document_types`
- `allows_estimate`

`checklist_templates` и `checklist_template_items` описывают шаблон чек-листа.

### 4.5.2. Типы полей чек-листа

Для `MVP` недостаточно только `checkbox`, `text` и `photo`. Нужно заложить расширяемую модель ответов, минимум:

- `boolean`
- `text`
- `number`
- `date`
- `photo`
- `file`
- `signature`
- `geopoint`
- `serial_number`
- `select`

Поэтому в `checklist_answers` лучше хранить:

- `value_jsonb`
- `item_type`
- `completed_at`
- `updated_by`
- `device_id` - для мобильного контура
- `client_uid` - для идемпотентной синхронизации
- `version`

### 4.5.3. Экземпляры чек-листов

`checklist_instances` должны создаваться автоматически на основе `process_template` и вида работ заявки.

Обязательные поля:

- `id`
- `application_id`
- `application_equipment_id` - опционально, но крайне желательно для заявок с несколькими единицами оборудования
- `template_id`
- `status` (`draft`, `in_progress`, `completed`)
- `assigned_to_user_id`
- `started_at`
- `completed_at`

Привязка к `application_equipment_id` нужна, чтобы не потерять историю по конкретной единице оборудования внутри одной заявки.

### 4.5.4. Правила заполнения

- обязательные пункты не позволяют завершить чек-лист;
- права на изменение есть только у назначенного исполнителя или уполномоченного руководителя подрядчика;
- заказчик может просматривать чек-листы, но не редактирует исполнительскую часть;
- при изменении шаблона уже созданные экземпляры не переписываются;
- backend валидирует ответы по типу поля, а не только по факту непустого значения.

### 4.5.5. Офлайн-синхронизация мобильного клиента

Backend должен поддерживать:

- батчевую загрузку ответов и вложений;
- идемпотентные операции по `client_uid` или `idempotency_key`;
- optimistic locking по `version`;
- отдельный статус синхронизации файлов;
- безопасную повторную отправку одного и того же офлайн-пакета без дублей.

Офлайн-синхронизация является обязательной частью архитектуры `MVP`, а не post-MVP улучшением.

`cost_estimate_items`:

- `total_price`

### 4.6.2. Бизнес-правила

- подрядчик формирует и отправляет смету;
- заказчик согласует или отклоняет смету;
- изменение сметы после отправки должно создавать новую ревизию, а не перетирать старую;
- актуальная согласованная смета должна быть доступна в карточке заявки и в документах.

В `MVP` отдельный объект сметы обязателен. Его отсутствие в backend-модели является функциональным пробелом.

## 4.7. Материалы и склады

### 4.7.1. Сущности

- `material_catalog`
- `warehouses`
- `warehouse_stocks`
- `material_operations`

`material_catalog` - единый справочник номенклатуры.

`warehouses` должны поддерживать склады:

- заказчика;
- подрядчика;
- сервисного центра;
- при необходимости мобильной бригады или выездного запаса.

`warehouse_stocks` хранит текущий остаток материала на складе.

`material_operations` - обязательная сущность, потому что `audit_log` недостаточно для продуктового учета материалов. Минимальные поля:

- `id`
- `material_id`
- `from_warehouse_id` - опционально
- `to_warehouse_id` - опционально
- `application_id` - опционально
- `operation_type`
- `source_type` (`customer_stock`, `contractor_stock`, `purchase_for_application`)
- `quantity`
- `unit`
- `unit_cost` - опционально
- `performed_by`
- `comment`

### 4.7.2. Обязательные типы операций

Для `MVP` нужно поддержать как минимум:

- `receipt`
- `reserve`
- `issue`
- `transfer`
- `return`
- `writeoff`
- `adjustment`

### 4.7.3. Бизнес-правила

- система должна показывать источник материалов по заявке;
- резервирование и списание должно быть связано с конкретной заявкой;
- перенос между складами выполняется атомарно;
- списание не может уводить остаток в отрицательное значение;
- передача материалов заказчика подрядчику должна быть отражаемой как отдельная операция;
- закупка под заявку должна быть видна как отдельный источник, а не смешиваться со складским остатком подрядчика.

Текущая модель с одной таблицей `Materials` и опорой только на `audit_log` для движения материалов недостаточна для требований `README` и `PRD`.

## 4.8. Коммуникации и вложения

### 4.8.1. Сущности

- `threads`
- `messages`
- `attachments`

`threads` должно поддерживать контекст:

- `application`
- `estimate`
- `materials`
- `general`

`attachments` должны быть универсальными и уметь привязываться к:

- заявке;
- сообщению;
- ответу чек-листа;
- смете;
- документу;
- договору.

Минимальные поля `attachments`:

- `id`
- `owner_type`
- `owner_id`
- `file_name`
- `mime_type`
- `file_size`
- `storage_key`
- `uploaded_by`

### 4.8.2. Бизнес-правила

- файлы не должны храниться отдельными несвязанными таблицами под каждый модуль, если можно использовать общий attachment-контур;
- выдача ссылок на скачивание должна идти через ограниченные по времени `presigned URL`;
- права доступа к вложению наследуются от сущности-владельца.

- `template_id` - опционально
- `visible_for_customer`
- `visible_for_contractor`
- `created_by`
- `generated_at`

### 4.9.2. Бизнес-правила

- backend должен поддерживать как загрузку документов, так и генерацию по шаблонам;
- документы должны храниться в контексте заявки;
- должна быть простая версионность;
- документы фильтруются по виду работ и правам доступа;
- авансовая отчетность и закрывающие документы подрядчика входят в `MVP`;
- юридически значимая подпись и сложный workflow согласования документов не входят в `MVP`.

## 4.10. Уведомления

На старте достаточно email-уведомлений и асинхронной отправки через background jobs.

События, которые стоит поддержать в `MVP`:

- инвайт пользователя;
- сброс пароля;
- назначение заявки подрядчику;
- назначение бригады или инженера;
- отправка сметы на согласование;
- согласование или отклонение сметы;
- завершение заявки подрядчиком;
- приемка результата заказчиком.

Push и in-app уведомления допускаются как следующий этап.

## 4.11. Базовая аналитика

В `MVP` модуль аналитики должен закрывать базовую прозрачность, а не полный BI-контур.

Обязательные срезы:

- заявки по статусам и видам работ;
- сроки исполнения;
- история по оборудованию;
- загрузка и результативность бригад;
- материалы и стоимость в разрезе заявок.

Допустимая реализация на старте:

- SQL-агрегации поверх основной БД;
- кэширование тяжелых запросов в `Redis`;
- при необходимости - materialized views или отдельные read-модели.

`AI`-прогнозирование и расширенная предиктивная аналитика не являются обязательной частью `MVP`.

## 4.12. Аудит-лог

### 4.12.1. Сущность

Таблица `audit_log` должна хранить:

- `id`
- `actor_user_id`
- `organization_id`
- `action`
- `entity_type`
- `entity_id`
- `old_values` (`JSONB`)
- `new_values` (`JSONB`)
- `meta` (`JSONB`)
- `created_at`

### 4.12.2. Что обязательно логировать

- смену статусов заявки;
- создание и изменение смет;
- операции с материалами;
- загрузку и генерацию документов;
- изменения прав доступа и оргструктуры;
- события входа, выхода и сброса пароля.

`audit_log` не заменяет продуктовые таблицы движения материалов, статусов и версий документов. Он дополняет их.

# 5. Сквозные backend-требования

## 5.1. API и контракт взаимодействия

- базовый namespace: `/api/v1`;
- все create/sync операции для мобильного контура должны поддерживать `idempotency`;
- листинги должны иметь пагинацию, сортировку и фильтрацию;
- тяжелые файловые upload/download операции должны идти через `presigned URL`;
- важные state-changing операции должны быть транзакционными.

## 5.2. Безопасность

- весь внешний трафик только по `HTTPS`;
- пароли хранятся как `bcrypt`/`argon2` hash;
- обязательны rate limiting, tenant isolation и server-side проверки прав;
- прямой доступ к чужим данным по `UUID` должен быть невозможен;
- CORS и политики доступа к объектному хранилищу должны быть явно настроены.

## 5.3. Фоновые задачи

В отдельные воркеры или job queue должны быть вынесены:

- отправка email;
- генерация документов;
- обработка тяжелых batch sync операций;
- импорт данных из внешних систем, если он появится.

## 5.4. Интеграции и границы первой версии

Для `MVP` допускаются только минимально необходимые интеграции.

На старте не следует делать обязательными:

- интеграцию с `1С`;
- `AI`-прогнозирование;
- юридически значимый документооборот;
- сложные двусторонние ERP-синхронизации.

Эти направления должны оставаться расширяемыми, но не определяющими для первой версии backend.
